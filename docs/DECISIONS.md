## ADR-0001: اعتماد branch `stabilization/baseline-and-security` كفرع العمل التأسيسي

- **السياق:** الفرع `main` يحمل baseline غير محمي؛ الخطة المرجعية §1.1 تأمر بفرع تثبيت قبل أي ميزة.

- **النتائج:** حماية main من كسور وسيطة؛ يتطلب انضباط rebase.

## ADR-0003 (مسودة): مصير الأحداث المالية المعلنة في README
- **التاريخ:** 2026-08-24 — **حالة: مُقترح، غير معتمد بعد**
- **السياق:** README يعد بسحب مخزون وقيود آلية عبر أحداث، والكود يحتوي `emit` في موضعين **بلا أي listener**. EventEmitter2 in-process لا يضمن ذرية مع قاعدة البيانات.
- **الخيارات:** (أ) outbox pattern (جدول أحداث + معالج) — أثقل لكن موثوق وقابل للتدقيق. (ب) تنفيذ الآثار داخل نفس `prisma.$transaction` وإسقاط ادعاء الأحداث — أبسط وأكثر أمانًا محاسبيًا. (ج) إبقاء events in-process للتنبيهات غير المالية فقط (low stock notifications).
- **القرار المقترح:** (ب) للآثار المالية + (ج) للتنبيهات التشغيلية، وإعادة كتابة README ليعكس الحقيقة. يُحسم نهائيًا في المرحلة 2/7.
- **الاسترجاع:** لا ينفذ شيء قبل الاعتماد.

## ADR-0005: تقييد النشر الشبكي وpgAdmin اختياري في docker-compose
- **التاريخ:** 2026-08-25 (GF-0006)
- **السياق:** P1-06 — الخدمات كانت منشورة على كل الواجهات (`0.0.0.0`) بكلمات مرور ثابتة، وpgAdmin يعمل دائمًا ببيانات ضعيفة.
- **الخيارات:** (أ) إبقاء النشر الشامل للراحة التطويرية — مرفوض: بيئة التطوير على شبكات غير موثوقة أمر شائع. (ب) ربط localhost فقط + pgAdmin تحت profile اختياري — مُعتمد.
- **القرار:** كل الـ ports تصبح `127.0.0.1:...`، وpgAdmin تحت `--profile tools` لا يعمل افتراضيًا، وكل البيانات من `.env` بصيغة `${VAR:?msg}` (فشل تشغيل عند النقص).
- **النتائج:** الوصول من أجهزة أخرى (مثل الهاتف الفعلي للمحاكاة) يتطلب SSH tunnel أو تعديلًا واعيًا — مقبول للأمان. للتطوير الميداني لاحقًا يُضاف binding مؤقت موثق.
- **الاسترجاع:** revert الملف — لا أثر على الكود.
- **الاعتماد:** قاعدة 0.5 من الخطة المرجعية (الأمن أولًا).

## ADR-0007: منع الرصيد السالب مطلقًا (سياسة المخزون)
- **التاريخ:** 2026-08-25 (GF-0007)
- **السياق:** أول مهمة schema للمخزون تتطلب حسم سياسة الرصيد السالب: هل يُسمح بصرف أكثر من الرصيد (oversell) بصلاحية خاصة، أم يُمنع؟ في مصنع ملابس، رصيد سالب يعني أحد ثلاثة: بيانات جرد فاسدة، أو عملية غير موثقة، أو خلل تزامن — كلها أعطال يجب كشفها لا تمييعها.
- **الخيارات:** (أ) منع مطلق على مستوى الخدمة وقاعدة البيانات معًا — مُعتمد. (ب) سماح بصلاحية (allow-negative بقرار INVENTORY_MANAGER+) — مرفوض الآن: يحتاج نظام صلاحيات أدق وسيناريو أعمال حقيقيًا لم يُطلب بعد، ويخلّ بقابلية المطابقة `currentStock == SUM(ledger)`. (ج) منع على مستوى الخدمة فقط — مرفوض: أي مسار مستقبلي يتحاوز الخدمة يفتح الثغرة.
- **القرار:** منع مطلق بثلاث طبقات: فحص داخل `prisma.$transaction` يرمي 400 (rollback كامل)، وقيد CHECK على `raw_materials` في قاعدة البيانات نفسها (defense-in-depth)، وقيد `quantityDelta` موقعة في الـ ledger بحيث الرصيد المطابَق لا يمكن أن يهبط تحت الصفر دون كسر قاعدة البيانات.
- **النتائج:** الصرف/الهدر/التسوية التي تُظهر الرصيد سالبًا تُرفض برسالة عربية واضحة تدفع لتسوية الجرد أولًا. أي سماح مستقبلي بعبور الصفر = ADR جديدة + migration + مبرر تشغيلي موثق.
- **الاسترجاع:** قرار قابل للعكس بـ migration جديدة (حذف CHECK) — لكن رجوعه العملي مستبعد.
- **الاعتماد:** بطاقة GF-0007 (معيار القبول 6).

## ADR-0008: التكلفة بمتوسط مرجح (Weighted Average) — مرحليًا
- **التاريخ:** 2026-08-25 (GF-0007)
- **السياق:** تقييم حركات المخزون يحتاج سياسة تكلفة معتمدة. الخامة تُشترى بأسعار متغيرة، والمصنع يحتاج تكلفة حالية واحدة للخامة تُستخدم في تقييم الصرف والهدر وحساب تكلفة الإنتاج.
- **الخيارات:** (أ) متوسط مرجح بسيط — مُعتمد: تكلفة الوحدة الجديدة = (رصيد×تكلفة حالية + كمية الشحنة×تكلفة الشحنة) / الرصيد الجديد، يُعاد احتسابها داخل نفس `$transaction` الاستلام. (ب) FIFO بطبقات — أدق محاسبيًا لكنه يحتاج جدول طبقات تكلفة ومنطق استهلاك أعمق، مؤجل بلا طلب أعمال حالي. (ج) تكلفة آخر شحنة (LIFO-like) — أبسط لكنه يشوه التقييل عند تقلب الأسعار.
- **القرار:** متوسط مرجح (أ) كسجل في `RawMaterial.costPerUnit`، وتقييم الصرف/الهدر/التسوية بهذه التكلفة الحالية لحظة الحركة (`unitCost` + `totalValue` في سطر الـ ledger). الاستلام على رصيد صفري يعتمد تكلفة الشحنة مباشرة.
- **النتائج:** دقة `costPerUnit` منزلتان عشريتان (10,2) — فروق تقريب طفيفة بين `SUM(totalValue)` و(الرصيد×التكلفة) مقبولة وموثقة هنا. الانتقال لـ FIFO لاحقًا = ADR جديدة + migration لجدول الطبقات، والـ ledger الحالي صالح أساسًا لها (كل حركة موثقة بتكلفتها).
- **الاسترجاع:** تبديل المعادلة في InventoryService داخل نفس البنية (revert كود فقط).
- **الاعتماد:** بطاقة GF-0007 (معيار القبول 6).
