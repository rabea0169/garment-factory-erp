# قائمة فحص مراجعة PR — GF-ERP (إلزامية)

> **CC-5 (GF-IMP-W2 — الجزء السياساتي):** هذه القائمة معيار مراجعة ملزم لكل
> Pull Request يُفتح على هذا المستودع — بدءًا من الموجة الثانية (GF-IMP-W2)
> وما بعدها في كل الموجات القادمة. لا يُدمج أي PR قبل تعبئة الفحص أدناه
> وتأكيد كل بند إلزامي (☐ → ☑ مع دليل أو رقم سطر/ملف عند الملاحظة).

## 1. ActivityLog داخل المعاملة (SEC-F02) — إلزامي

- [ ] كل كتابة مالية أو مخزنية جديدة (رصيد خزينة/عميل/مورد/حساب، حركة
      مخزون، قيد GL) تكتب سجل `ActivityLog` **داخل نفس `$transaction**
      التي تجري الكتابة** — لا بعدها ولا خارجها.
- [ ] السجل يحمل: معرف الكيان المتأثر (`payrollId` / `journalEntryId` /
      `stockLedgerId` ...)، هوية الفاعل (`userId` من الجلسة)، والقيم الجوهرية
      (المبلغ/الكمية قبل وبعد عند توفرها).
- [ ] فشل كتابة السجل يُرجع المعاملة كلها (السجل جزء من الأثر الذري،
      وليس "تسجيلًا أفضل-جهد" ينفصل عن الكتابة).

**دليل الفحص:** في الـ PR، لكل مسار كتابة جديد: `grep` على
`activityLog.create` داخل نفس دالة الـ transaction، أو بيان أن المسار
يُحدّث سجلًا قائمًا داخل معاملة موجودة.

## 2. Idempotency-Key لكل POST مالي/مخزني — إلزامي

- [ ] كل `POST` جديد يمس مالًا أو مخزونًا يستقبل ترويسة `Idempotency-Key`.
- [ ] عند تكرار المفتاح: تُعاد الاستجابة المخزنة نفسها (replay) بلا أثر
      ثانٍ — لا إنشاء ثانٍ ولا 409 أعمى.
- [ ] مفتاح مع محتوى طلب مختلف → 409 برسالة عربية واضحة.
- [ ] مفتاح الترحيل المالي (`postingKey`) ثابت واشتقاقه قابل للإعادة
      (مثل `hr-payroll-pay:<id>`) كي تحمي طبقة GL نفسها من التكرار.

**دليل الفحص:** مراجعة الـ controller (الترويسة تُمرر للخدمة) + اختبار
replay في مواصفة الخدمة.

## 3. الأحداث بعد commit فقط — إلزامي

- [ ] لا `emit`/`emitAsync` لأي حدث داخل `$transaction` قبل نجاحها —
      الحدث الذي يُبث قبل commit حدث عن عملية قد تُرجَع (حدث وهمي).
- [ ] النمط المعتمد: جمع الأحداث في مجمع (collector) يمرَّر عبر مسار
      المعاملة، ثم بثها بعد نجاح `$transaction` فقط (نمط INV-1 في
      `InventoryService`/`consumeMaterial`).
- [ ] البث fire-and-forget (`void promise`) كي لا يفشل مستمعٌ عمليةً
      ملتزمة، مع ترتيب مضمون وموثق بالاختبارات.

## 4. المبالغ Decimal بلا تحويل float — إلزامي

- [ ] أي حقل `Decimal` في Prisma يُعامل بـ `Prisma.Decimal` (أو
      `Decimal` من decimal.js) — **ممنوع** `Number(row.amount)` ثم
      جمع/طرح float.
- [ ] التحويل الرقمي مسموح فقط عند حدود العرض/الاستجابة
      (`.toNumber()` للـ DTO النهائي) أو بعد تقييد المنازل
      (`round2`/`round4` بنمط purchasing).
- [ ] المقارنات المالية الكسرية عبر Decimal (لا `0.1 + 0.2 > 0.3` خامًا).
- [ ] الـ DTOs تستخدم `@IsNumber({ maxDecimalPlaces })` لقصر مدخلات
      العميل على دقة الأعمدة.

## 5. أخطاء Prisma لا تصل العميل خامًا — إلزامي

- [ ] أي استعلام جديد يمر عبر `GlobalExceptionFilter` الذي يحوّل
      P2025→404، P2003→400، P2002→409 برسائل عربية موحدة — لا 500
      بكومة Prisma أمام العميل.
- [ ] المسارات الحساسة ترفض الحالات المستحيلة بـ `NotFoundException`/
      `ConflictException`/`BadRequestException` عربية **قبل** الكتابة
      (فحص الوجود/الحالة داخل المعاملة).
- [ ] الشفرة غير المعروفة تبقى 500 عام مع structured log للـ ops
      (requestId + stack) — لا تسريب تفاصيل القاعدة للعميل.

## كيف تطبق القائمة

1. يفتح كاتب الـ PR القسم أعلاه في وصف الـ PR ويعلّم كل بند مع دليل
   مختصر (ملف/سطر أو اسم الاختبار).
2. أي بند غير منطبق على تغيير الـ PR يُعلَّم "لا ينطبق" **مع سبب**
   (مثل: PR توثيقي فقط / لا يمس مالًا ولا مخزونًا).
3. المراجع يرفض الدمج عند أي بند إلزامي بلا تعليم أو بلا دليل.
4. هذه القائمة تتوسع بموجات التحسين: أي إصلاح من نوع P0/P1 يضيف بندًا
   إلزاميًا جديدًا هنا في نفس الـ PR (مصدر الحقيقة واحد).
